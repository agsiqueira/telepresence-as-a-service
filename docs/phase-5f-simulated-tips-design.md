# Phase 5F — Simulated Tips design contract

## 1. Purpose and product contract

Phase 5F adds a small post-Journey simulation in which the Explorer may record one preset Tip for the Teleporter who performed that Journey. This is not a financial transaction. Every participant-facing submission surface must state: **“This is a simulation. No money will be charged or transferred.”**

Only persisted Journey participation is authoritative. The Explorer is the Journey's `viewerId`; the Teleporter is its non-null, distinct `operatorId`. Current account roles, capabilities, profiles, Agreement terms, client fields, and display names never determine attribution.

Eligible amounts are USD $5, $10, $15, and $20, stored as integer minor units `500`, `1000`, `1500`, and `2000`. Currency is server-owned `USD`. Tip amount and currency are independent of Agreement price and currency.

Both immediate and scheduled completed Journeys qualify, including historical completed Journeys. No historical Tip is fabricated. Absence of a Tip remains absence; no zero-dollar or “No Tip” record is stored.

## 2. Domain model

Add a dedicated `SimulatedTip` model:

| Field | Contract |
|---|---|
| `id` | UUID primary key generated by the database/Prisma |
| `tripId` | Unique Journey foreign key; one Tip per Journey |
| `explorerId` | Server-derived Journey Explorer |
| `teleporterId` | Server-derived Journey Teleporter |
| `amountMinor` | One of `500`, `1000`, `1500`, `2000` |
| `currency` | Server-owned ISO `USD`, stored as `CHAR(3)` |
| `submittedAt` | Database-generated `TIMESTAMPTZ(3)` |

Use a composite Journey relation from `(tripId, explorerId, teleporterId)` to the existing unique Trip participant tuple `(id, viewerId, operatorId)`. User relations for Explorer and Teleporter use `onDelete: Restrict`; the Journey relation also uses `onDelete: Restrict`. `tripId` is unique. Add indexes only where needed for participant history reads, such as `(explorerId, submittedAt)` and `(teleporterId, submittedAt)`.

Do not persist performed-role columns. Matching the composite Journey positions proves the Explorer and Teleporter performed roles without duplicating mutable account-role information.

All stored fields are server-owned except that authenticated Explorer input selects the allowed `amountMinor`. The client never supplies Trip participants, recipient, roles, currency, timestamps, status, Agreement values, or payment data.

The existing completed-Journey authority fields—`viewerId`, `operatorId`, completed `status`, and `endedAt`—remain immutable under the Phase 5D.1 database safeguard. Phase 5F must preserve that mechanism.

## 3. Database integrity

A forward-only migration must:

- create only the `SimulatedTip` table, relations, narrow indexes, constraints, and trigger functions required by this phase;
- enforce one Tip per Journey with a unique constraint;
- enforce exact Journey participant attribution through the composite relation and an insertion trigger where cross-table status validation is required;
- accept only `ENDED` or `FEEDBACK_COMPLETED` Journeys with `endedAt` set and two distinct persisted participants;
- enforce `amountMinor IN (500, 1000, 1500, 2000)`, which also proves a positive integer minor-unit amount;
- enforce `currency = 'USD'`;
- reject updates and deletes so a Tip is immutable;
- use narrow, descriptive constraints and trigger names with errors that services can translate into bounded domain responses;
- remain transaction-safe under concurrent duplicate creation.

The insertion trigger must validate the authoritative Trip row even for direct SQL that bypasses application services. It must not consult current `User.role`, capabilities, account status, Agreement price, Review state, Feedback, or Safety content.

The migration must not backfill, update, delete, or reinterpret any existing Trip, Agreement, Review, Feedback, Safety, restriction, or account row. It must add no payment, processor, transfer, payout, or settlement table or column.

## 4. Service contract

### Read

An authenticated persisted Journey participant may read the Tip state for that Journey. This includes inactive or safety-restricted historical participants. Unrelated users, guessed Journey IDs, and Journeys whose persisted participant pair does not include the caller receive the same privacy-safe not-found result.

The read result contains only:

- eligibility for a new Explorer submission;
- the counterparty's privacy-safe display name and performed role where appropriate;
- the immutable Tip receipt if one exists;
- the simulation disclaimer.

It contains no internal IDs, account status, restriction state, authorization reasoning, Agreement price, payment state, hidden Review information, Feedback, or Safety data.

### Submit

Submission must execute transactionally:

1. Lock/read the authoritative Trip.
2. Derive Explorer and Teleporter from persisted participation.
3. Require the caller to be that Explorer.
4. Require `ENDED` or `FEEDBACK_COMPLETED`, `endedAt`, and a distinct assigned Teleporter.
5. Require the Explorer's account to be active and free of an effective account-safety restriction at transaction time.
6. Validate the approved amount and assign currency `USD` server-side.
7. If an existing Tip has the same amount, return its original receipt with `created: false`.
8. If an existing Tip has a different amount, return a stable conflict.
9. Otherwise insert exactly one immutable Tip and return `created: true`.

An inactive or restricted Teleporter does not invalidate an otherwise eligible historical Journey or hide an existing receipt. The submission gate applies to the Explorer initiating new Tip activity. Current account roles or later capability changes do not alter historical attribution.

Concurrent identical submissions create exactly one row and both resolve to the same immutable receipt, either directly or through the established bounded retry contract. Concurrent different-amount submissions leave exactly one stored amount; the loser receives the stable changed-retry conflict. No partial state exists outside the Tip row.

Stable domain categories:

- `INVALID_SIMULATED_TIP` — malformed amount or request shape;
- `JOURNEY_NOT_FOUND` — missing, unrelated, or privacy-protected Journey;
- `JOURNEY_NOT_COMPLETED` — Journey has not reached an eligible completed state;
- `SIMULATED_TIP_UNSUPPORTED` — incomplete or invalid persisted participant snapshot;
- `SIMULATED_TIP_SUBMISSION_RESTRICTED` — inactive or effectively restricted Explorer;
- `SIMULATED_TIP_ALREADY_SUBMITTED` — different-amount retry;
- `SIMULATED_TIP_CHANGED_CONCURRENTLY` — bounded retryable transaction conflict.

Errors must not reveal the Teleporter's account state, another participant's activity, Safety information, or internal authorization decisions.

## 5. API contract

Provide participant-authorized Journey-scoped endpoints:

- `GET /api/trips/[id]/simulated-tip`
- `POST /api/trips/[id]/simulated-tip`

The POST body is exactly:

```json
{ "amountMinor": 500 }
```

`amountMinor` must be exactly one of `500`, `1000`, `1500`, or `2000`. Reject missing, repeated, fractional, string, boolean, null, array, nested, oversized, malformed, prototype-pollution-shaped, or unknown properties. Explicitly reject client-provided participant/recipient IDs, roles, currency, timestamps, status, Journey or Agreement authority fields, Review state, account fields, and all payment concepts.

A successful POST returns a bounded receipt:

```json
{
  "simulatedTip": {
    "amountMinor": 500,
    "currency": "USD",
    "submittedAt": "2026-08-02T12:00:00.000Z",
    "recipient": { "displayName": "Teleporter", "performedRole": "TELEPORTER" }
  },
  "created": true
}
```

The successful GET projection returns the caller-authorized eligibility and the same receipt shape when a Tip exists. The Explorer and Teleporter may both read the receipt immediately after creation. Absence is represented as `simulatedTip: null`, never as a zero amount. Endpoint names and responses must use “simulated Tip” language and must not imply charge, transfer, balance, payout, or payment processing.

## 6. Participant UI

Preserve current dashboard, completed-history, responsive, and visual conventions.

### Explorer states

- Completed eligible Journey with no Tip: show a compact entry point from completed-Journey history/detail, the Teleporter's privacy-safe display name and performed-role label, four native accessible amount choices, and the required simulation disclaimer before submission.
- Submitting: lock against double action, disable the control with understandable text, and announce progress.
- Success: show the immutable amount/currency, recipient display name/role, submission time, disclaimer, and that the simulated Tip cannot be edited, replaced, withdrawn, or deleted.
- Identical retry/reload: restore the durable original receipt without creating another record.
- Changed retry: preserve the authoritative receipt and show a bounded conflict message.
- Ineligible/unfinished Journey: do not offer submission; show a neutral unavailable state when the Journey is otherwise authorized.
- Inactive or restricted Explorer: show an authorized historical receipt read-only; if none exists, explain only that new simulated Tip submission is unavailable, without disclosing internal restriction details.
- Temporary failure: preserve the selected amount, announce a bounded error, provide retry, and move focus predictably.

### Teleporter states

Completed-Journey history/detail may show the immutable Tip immediately after submission, with Explorer privacy-safe display name, performed-role context, amount/currency, submission time, and simulation disclaimer. The Teleporter receives no submit, edit, replace, withdraw, or delete control. Inactive or restricted Teleporters retain authorized historical read-only visibility.

Entry points and receipts must survive navigation and reload through authoritative GET state. Do not use local or session storage as authority.

## 7. Accessibility

- Use native radio inputs or an equivalently complete accessible single-choice control for all four amounts.
- Give each option an accessible name such as “5 US dollars simulated Tip” and preserve keyboard operation and selected-state semantics.
- Include text equivalents for selected amounts; do not rely on color.
- Associate validation messages with the amount group.
- Present the simulation disclaimer as visible text before submission and within the receipt.
- Announce submitting, success, restored receipt, conflicts, and failures with appropriate live regions.
- Move focus predictably to the receipt after success and to the error summary after failure.
- Keep disabled/loading states understandable without color and retain established minimum touch targets and focus indicators.

## 8. Privacy and domain isolation

Tip services, APIs, UI, projections, and tests must not expose or allow inference of:

- hidden Review submission, content, counts, or reveal timing;
- Explorer or Teleporter reputation inputs or calculations;
- private research Feedback;
- Safety Reports, conversations, restrictions, internal reasoning, Administrator identities, assignments, events, or notes;
- internal participant IDs or authorization decisions;
- Agreement price as a payment, charge, balance, or Tip basis;
- payment-provider concepts, credentials, customer IDs, methods, tokens, transfer IDs, or payout identifiers.

Tips never change Review visibility or reputation, Feedback, Safety state, restrictions, Agreement values, reservations, rescheduling, Trip status, account roles, capabilities, or marketplace eligibility.

## 9. Acceptance criteria and verification

Implementation is complete only when validators and focused tests prove:

### Structure and migration

- the dedicated immutable model and forward-only migration contain only Phase 5F objects;
- composite Journey attribution, unique Journey cardinality, amount choices, forced USD, insert eligibility, update prevention, and delete prevention are database-enforced;
- the migration has no backfill or historical rewrite and introduces no payment dependency or semantics.

### Service, API, and authorization

- only the persisted Explorer can submit to the persisted Teleporter;
- immediate, scheduled, newly completed, and historical completed Journeys qualify;
- incomplete, cancelled, unrelated, missing-operator, and same-participant Journeys are rejected appropriately;
- current role/capability changes do not change historical attribution;
- inactive or effectively restricted Explorers cannot submit;
- both participants, including inactive/restricted participants, retain authorized historical reads;
- allowed amount boundaries and server-forced USD are exact;
- unknown and server-owned properties are rejected;
- unrelated and guessed Journey reads are privacy-safe;
- identical retry is idempotent, changed retry conflicts, and concurrent duplicate/different submissions store exactly one row.

### UI and accessibility

- completed-history entry points persist after navigation and reload;
- Explorer selection, confirmation, double-click prevention, receipt restoration, conflict, unavailable, and temporary-failure states work;
- Teleporter visibility is immediate and read-only;
- all four amount choices are labeled, keyboard operable, and expose selected state;
- disclaimer, progress, error, and success messages are visible and announced with predictable focus.

### Isolation

- Tip creation/read does not change or expose Reviews, reveal timing, either reputation, private Feedback, Safety Reporting/restrictions, Agreement price/currency, reservations, rescheduling, or Journey status;
- no zero/no-Tip row, custom amount, Tip editing/deletion, payment library, or processor identifier exists.

Add dedicated Phase 5F structural, service/API/privacy, UI/accessibility, PostgreSQL integrity, historical-data, and independent-concurrency validators/suites. Database runners must require the approved disposable variables, verify matching identities where required, differ from `DATABASE_URL`, authenticate before mutation, never fall back, and never print credentials or complete URLs.

Implementation verification must also run the relevant existing Journey lifecycle and concurrency suites; Agreement and scheduled-reservation/rescheduling suites; Phase 5D.1/5D.2 Review suites; private Feedback reload; Safety Reporting and Phase 4D restriction isolation; three-role and account-access synchronization; active-visit recovery; participant UI and terminology regressions; Prisma format/validate/generate; TypeScript `--noEmit`; repository-wide ESLint; production build; and `git diff --check`.

## 10. Migration and historical-data policy

Before database changes, inspect the approved disposable database using only the explicit test variables and report counts, never participant content or identifiers. Historical completed Journeys are eligible prospectively, but no historical Tip row is created until an eligible Explorer explicitly submits after Phase 5F deployment.

Do not populate Tips from Agreement prices, Reviews, Feedback, or any existing amount. Do not rewrite completed Journey participants or timing. If existing Journey rows cannot satisfy the proposed attribution or eligibility constraints, report categories/counts before adopting any destructive or semantic remediation.

## 11. Phase boundary

Phase 5F excludes:

- real charges or transfers;
- Stripe or any payment processor;
- payment methods, balances, payouts, refunds, fees, taxes, settlement, or chargebacks;
- custom Tip values;
- editing, deletion, replacement, or withdrawal;
- zero-dollar or “No Tip” persistence;
- tipping by the Teleporter;
- Tip-derived Review reveal or reputation;
- Phase 6 Live Moments or Guided Experiences;
- supply publication, scheduling, pricing, capacity, pause, archive, or expiration;
- Phase 7 visual redesign;
- maps, photos, sharing, richer chat, notifications, or real payments.

After Phase 5F is implemented and checkpointed, the original Phase 5 may be checkpointed as complete. Phase 6 and Phase 7 require separate approval and design work.
